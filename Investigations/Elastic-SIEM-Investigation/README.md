# Elastic SIEM Investigation

**Status:** Completed  
**Platform:** Elastic Security (Elastic Cloud)  
**Endpoint:** Windows 10  
**Focus:** SIEM | Windows Event Log Analysis | Detection Engineering | Authentication Monitoring

## Overview

This investigation involved deploying Elastic Agent to a Windows endpoint, collecting Windows security and system telemetry, and using Elastic Security to investigate authentication activity.

I reviewed successful and failed Windows logon events, created a custom ES|QL detection rule to identify repeated failed logons, and investigated the alert generated by the rule.

The aim was to gain practical experience with SIEM deployment, log analysis, detection rules and alert investigation.

## Objectives

- Deploy Elastic Agent and connect a Windows endpoint to Elastic Security.
- Collect and review Windows security events.
- Investigate successful and failed authentication activity.
- Create a custom detection rule using ES|QL.
- Generate and investigate an alert.
- Document findings and potential security improvements.

- **4625:** Failed logon
- **4634:** Account logoff
- **4647:** User-initiated logoff

## Failed Logon Investigation

I used a local test account named `SOC-LabUser` to generate controlled failed login attempts and examine how Windows recorded them.

The investigation identified four Event ID 4625 records for this account on the same endpoint.

The events occurred in two separate pairs:

| Time | Event ID | Account |
|---|---:|---|

| 15:35:09 | 4625 | SOC-LabUser |
| 16:14:03 | 4625 | SOC-LabUser |

The first pair occurred approximately three seconds apart. The second pair occurred approximately two seconds apart.

The earlier failed logon records contained the following details:

## Detection Rule Creation

To identify repeated authentication failures, I created a custom ES|QL detection rule in Elastic Security.

**Rule name:** `Multiple Failed Windows Logons - SOC Lab`

**Description:**

Detects two or more failed Windows authentication attempts against the same user account on the same host within a five-minute period. Uses Windows Security Event ID 4625 collected through Elastic Agent. Intended to identify potentially suspicious repeated authentication failures for further investigation.

The query used was:

```sql
FROM logs-*
| WHERE event.dataset == "system.security"
  AND event.code == "4625"
  AND @timestamp >= NOW() - 5 minutes
| STATS failed_logons = COUNT(*) BY host.name, user.name
| WHERE failed_logons >= 2
| KEEP host.name, user.name, failed_logons
```

The query searches Windows Security logs for failed logon events, groups them by hostname and username, and counts the number of failures within the five-minute period.

Groups containing two or more failed logons are returned as detection results.

**Rule configuration:**

| Setting | Value |
|---|---|
| Rule type | ES\|QL |
| Severity | Medium |
| Risk Score | 47 |
| Schedule | Every 1 minute |
| Execution look-back | 2 minutes |
| Query time filter | 5 minutes |
| Minimum failed logons | 2 |

The rule was enabled and scheduled to run automatically.

## Alert Generation and Investigation

The detection rule successfully generated an alert at approximately 16:15.

The alert contained the following information:

| Field | Value |
|---|---|
| Rule | Multiple Failed Windows Logons - SOC Lab |
| Host | SOC-LAB-WINDOWS01 |
| User | SOC-LabUser |
| Failed Logons | 2 |
| Severity | Medium |
| Risk Score | 47 |
| Status | Open |

I initially noticed that the alert was generated approximately 40 minutes after the first two failed logon events. To investigate this, I reviewed the rule execution history and searched Discover for additional failed logons.

This identified another pair of failed logon events at approximately 16:14.

These events occurred shortly before the rule executed at 16:15.

The rule's query considered events from the previous five minutes. The original events from 15:35 were outside this window, whereas the two events from 16:14 were inside it.

This explains why the alert was generated at 16:15 rather than immediately after the earlier attempts.

The rule execution history also confirmed that the 16:15 execution succeeded and created one alert.

The alert reported two failed logons for the test account on the same host, matching the expected detection result.

## Findings

- Successfully deployed Elastic Agent and connected a Windows endpoint to Elastic Security.
- Collected and reviewed Windows Security, Sysmon and other endpoint telemetry.
- Identified successful and failed Windows authentication events.
- Investigated controlled failed logon attempts against a local test account.
- Created a custom ES|QL detection rule to identify repeated failed logons.
- Successfully generated a Medium severity alert for two failed logons within the detection window.
- Reviewed the rule execution history and confirmed that the execution responsible for the alert completed successfully.

The activity was generated as part of a controlled lab exercise. The alert demonstrated the detection of repeated authentication failures, but it did not represent a confirmed real-world brute-force attack.

## Recommendations

- Monitor repeated failed authentication attempts, particularly when they involve the same account or endpoint.
- Investigate unusual authentication patterns and review the associated Windows security events.
- Consider account lockout policies and appropriate authentication controls to reduce the risk of password-guessing attempts.
- Continue reviewing successful logons alongside failed attempts to establish a clearer picture of account activity.
- Tune detection thresholds to reduce false positives while maintaining useful detection coverage.

## Conclusion

This investigation provided practical experience deploying a cloud-based SIEM, collecting endpoint telemetry and investigating Windows authentication events.

I also gained experience creating an ES|QL detection rule, reviewing its execution history and investigating the alert it generated.

The project demonstrated how endpoint logs can be used to identify repeated authentication failures and generate alerts for further investigation.
